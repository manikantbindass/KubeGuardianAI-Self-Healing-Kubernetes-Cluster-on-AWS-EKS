# EKS plan, deployment and rollback runbook

Phase 03 is infrastructure code only. **No AWS apply, destroy or paid-resource creation is authorized by this runbook.** Application images currently have scan findings and the app is unauthenticated; local smoke success is not cloud production acceptance.

## Pre-plan gates

1. Select dev or production-like `demo`, account, region, owner, TTL and cost ceiling. Review [cost assumptions](../costs/eks-estimate.md), CIDR overlap and organizational controls. No environment is called production-ready.
2. Have an authorized administrator provision/reuse remote-state resources separately; follow [state bootstrap](terraform-state.md). Confirm least-privilege federated plan identity and backend access. The optional GitHub role only publishes ECR; it is not a Terraform administrator.
3. Verify regional EKS standard-support version, supported instance families/AZ quotas, AL2023 x86_64 AMI release, and compatible add-on builds. Pin values in ignored `.tfvars`, preserving the compatibility evidence. Read-only operator discovery examples:

   ```sh
   aws eks describe-addon-versions --kubernetes-version 1.34 --addon-name vpc-cni --region ap-south-1
   aws ssm get-parameter --name /aws/service/eks/optimized-ami/1.34/amazon-linux-2023/x86_64/standard/recommended/release_version --region ap-south-1
   ```

   Repeat add-on discovery for kube-proxy, coredns and eks-pod-identity-agent. Do not use example `v0.0.0` builds or placeholder AMI dates. These examples are not executed by validation CI.
4. Confirm existing Auto Scaling service-linked role and its ARN for KMS encrypted-node grants. Creating a missing service-linked role is an administrator-approved operation, not automatic here. Review KMS policies and future service-linked-role dependencies before plan.
5. Choose access principals and a **separate platform bootstrap path**. Creator cluster-admin is disabled and namespace Edit cannot install namespace/Role/RoleBinding foundations. The organization's platform administrator must explicitly authorize a narrowly time-bounded bootstrap/recovery procedure using EKS access management, create the `kubesentinel` namespace and scoped RBAC, then revoke temporary elevated access. This code does not grant cluster-admin or evade that approval gate. Do not expect a namespace deployer to bootstrap its own authority.
6. Decide private connectivity: private-only API needs a trusted VPC-connected workstation/runner (VPN/SSM path is not provisioned). An optional /24-or-narrower public API CIDR still requires authenticated EKS access; it is not application ingress. Verify NAT/endpoints and private DNS. No-NAT mode requires mirroring non-ECR images and dependencies.

## Validation and authorized planning

```sh
terraform fmt -check -recursive infrastructure/terraform
terraform -chdir=infrastructure/terraform/environments/dev init -backend=false -input=false
terraform -chdir=infrastructure/terraform/environments/dev validate
trivy config --severity HIGH,CRITICAL infrastructure/terraform
```

Copy and review `.tfvars.example` and backend example, then initialize the approved backend only with an authorized short-lived profile. Confirm identity/account using an operator-approved `aws sts get-caller-identity`; never print tokens or credential files. A read identity may lack refresh permissions for some resources. Do not grant administrator access just to silence plan errors.

After explicit plan permission, an operator can run `terraform -chdir=infrastructure/terraform/environments/dev plan -input=false -out=review.tfplan`. Treat the binary plan and rendered JSON as sensitive; both are ignored. Review replacements, IAM changes, public exposure, NAT/endpoints, KMS grants, access entries, AMI/add-on compatibility and projected cost. **Stop at the saved plan.** Any apply needs separate explicit authorization, a reviewed commit/lockfile/plan, and an appropriate execution identity. No live plan has been generated by this agent.

## Post-apply operator acceptance (future, unverified)

An authorized operator verifies private endpoint reachability, control-plane logs, add-on status, worker readiness, absence of public node IPs, encrypted EBS and IMDSv2, access denials and intended namespace access. Use `aws eks update-kubeconfig --name NAME --region REGION --alias sentinel-demo` only after access approval. No kubeconfig belongs in Git. Never alter a user's global context silently.

Mirror scanned API/dashboard images into the output ECR URLs with immutable commit tags. Upgrade image bases and triage Phase 02 findings before promotion. The optional GitHub publisher trust must match the actual repository/branch; use Actions `id-token: write` and short-lived OIDC only in a separately reviewed publish workflow.

Application deployment is a second stage: provision approved TLS PostgreSQL/Redis elsewhere, create a namespace Secret out of band (`DATABASE_URL`, `REDIS_URL`), and configure localStores=false. Never store secrets in Terraform variables, Helm values, plan logs or Git. Review the [Helm/cloud mappings](../architecture/local-vs-cloud.md); external stores need explicit NetworkPolicy/CNI allowances and trusted CA mounts. An ingress controller, internal LB/TLS, product authentication and notification endpoints are separately approved integrations. DNS is optional and references an already existing internal LB in an approved private zone; no LB or external DNS controller is silently installed.

## Rollback and failure handling

- Save reviewed configuration, locks and plan metadata before changes. Restore prior Terraform configuration and generate a **new** plan; reverting Git alone does not reverse AWS resources.
- Do not downgrade an EKS Kubernetes control-plane version: upgrades are not generally reversible. Prefer a tested parallel-cluster migration for incompatible changes. Preserve backups and rollback-compatible app/schema releases.
- Managed-node AMI updates need capacity, PDB and workload-drain review. Test staged node replacement; a one-node dev environment has planned disruption.
- If KMS/identity/network changes fail, stop and inspect events using authorized read access. Do not disable encryption, open 0.0.0.0/0 or attach AdministratorAccess as a workaround.
- Missing audit/flow/workload logs must be diagnosed independently; metric alarms without notification actions are not an on-call service. Exercise filter/retention/delivery once deployed.

## Cost-controlled teardown (operator approval required)

Set an owner/TTL and schedule a review; Terraform alone does not expire resources. Before any approved destruction: export required evidence/backups, remove Kubernetes ingress/services/controllers that created LBs/volumes, detach retained dependencies, review ECR retention and externally managed data, and inspect an authorized destroy **plan**. Destroy execution is a separate explicit approval. No destructive command is run or recommended as an unattended cleanup default.

Verify cluster, managed nodes/ASGs/EBS, ENIs, NAT/EIPs, interface endpoints, log groups, ECR images, KMS grants/aliases and optional DNS. ECR force-delete is false: existing images deliberately block removal until an owner approves disposition. State bucket/key prevent_destroy and must persist for audit/recovery; never remove them as part of an ephemeral environment teardown. KMS has a 30-day deletion window; verify it is not protecting retained volumes/logs. Check billing and resource inventory in the exact account/region after cleanup; successful Terraform exit is not proof of zero residual cost.
