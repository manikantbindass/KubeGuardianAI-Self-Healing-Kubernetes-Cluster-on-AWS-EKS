# ADR 0010: evidence-constrained incident intelligence

Status: implemented deterministic API; remote LLM integration disabled/unimplemented.

The intelligence engine reads the authenticated operations model: at most 100 incidents, 1000 namespace-scoped snapshots and 100 incident-linked anomaly records. Exact namespace/workload identity and a 15-minute window create related-incident links. Same-reason links in that window are duplicate candidates; records are retained, not deleted or silently suppressed. Older same-reason incidents in the same namespace provide limited historical similarity, which is categorical rather than learned/semantic similarity. Severity sorts attention; it cannot escalate execution rights.

The engine ranks a symptom investigation hypothesis plus a deployment-change association only when a recognized event precedes the incident in the same workload/window. Event messages and incident summaries never become instructions or templates. Kubernetes event owners must match exactly; no pod-prefix identity inference is used. Collected events and incident-linked metric anomaly evidence are correlated; raw logs and live metric time series are explicitly unavailable to this engine. There is no claim of comprehensive cross-signal root-cause analysis.

Retrieval uses a fixed, versioned catalog of four internal runbooks with explicit reason mappings and read-only steps. Unknown reasons select evidence collection. Every hypothesis carries evidence references and an uncertainty label. `incident:ID`, `event:ID` and `anomaly:ID` resolve against the authorized operations view; runbook citations are repository-relative paths/anchors. No user URL, file path, shell command or provider output controls retrieval. Responses omit raw incident summaries, logs, event messages, JWTs, signing keys and full Kubernetes objects.

The optional provider-agnostic `Assistant` protocol accepts copied typed hypotheses and may return known IDs only. Unknown IDs, malformed selections and exceptions use the unchanged deterministic fallback. Ranking/evidence remain deterministic. The production API never supplies an assistant, makes no remote calls and incurs zero provider spend. A future remote adapter requires separately reviewed egress, enforced timeouts/token budgets/cost accounting, consent and adversarial evaluation; the interface alone does not implement these controls or promise prompt-injection immunity. Raw logs must never enter an instruction channel.

The API requires viewer authentication, applies a Redis atomic 30-request/user/minute admission limit and fails closed if the limiter is unavailable. Namespace scope is the existing installation allowlist, not new per-user tenancy. Feedback requires operator authorization and existing mutation limits. It updates the existing latest incident review and appends an audit event containing redacted feedback; it does not issue remediation commands. There is no model retraining from feedback or claimed quality improvement. Replacing the latest review is visible behavior, and audit retention remains an operational requirement.

Alternatives include graph databases, vector retrieval and an LLM-generated narrative. A bounded deterministic engine is chosen because no representative causal labels or enterprise provider/privacy configuration exist yet. Its simple rules and tiny synthetic evaluation do not establish real-world accuracy. Multi-cluster grouping is intentionally absent until every signal has a trusted cluster identity; joining same-named workloads across clusters would be unsafe.

## API and operations

`GET /api/v1/ops/intelligence?mode=real&namespace=all&q=checkout` returns typed explanations, evidence, hypotheses, runbooks and missing-source/lag limitations. `GET /api/v1/ops/intelligence/runbooks` returns only the fixed catalog. `POST /api/v1/ops/intelligence/feedback` accepts an incident UUID, verdict (`supported`, `unsupported`, `insufficient-evidence`) and bounded note. Use an authorized bearer token via a protected client; do not paste credentials into logs or history. Real is default; demo remains explicit and disabled unless configured.

Existing incident ingestion deduplicates persistent fingerprints. New grouping only aids attention and does not silence alerts or mask unresolved records. Existing Alertmanager-to-incident ingestion remains the webhook integration: [observability routing](../runbooks/observability.md). No outbound notifications are sent. If adding outbound routing, require HTTPS destination allowlists, authentication/signatures, stable incident idempotency keys, bounded retries with dead-letter handling and secret-free payloads; never turn an analysis response into an executable webhook instruction.

## Threat model and limits

Threats include prompt injection in logs/notes, invented evidence, malicious assistant adapters, namespace confusion, temporal coincidence, secret/PII leakage, provider outages and cost amplification. Defenses are no raw text egress, fixed catalogs, exact identities/time checks, copied provider context, selected-ID validation, deterministic ranking, typed bounds, role checks, redaction and read admission limits. Regex redaction is best effort and is not comprehensive PII detection; omission and no egress are stronger controls. Adapter implementations are trusted code and cannot be safely sandboxed by a Python protocol.

Tests cover exact identity/window boundaries, preceding changes, unsupported recommendations, injected text, assistant outage, redaction, authentication, denied feedback and absence of command records. The [synthetic evaluation](../reports/phase-10/results.json) reports fixture-level correlation/retrieval results. Reproduce with `PYTHONPATH=apps/api uv run python scripts/evaluate_intelligence.py` (PowerShell: `$env:PYTHONPATH='apps/api'`). This is not held-out production evaluation. Existing anomaly-model metadata/drift remains separate; rule/catalog version and operator feedback are quality signals, not measured model drift or false-positive estimates. Live logs, remote LLM, broad historical search, automatic routing and multi-cluster inventory remain limitations.
